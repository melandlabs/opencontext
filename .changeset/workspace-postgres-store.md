Add a Postgres backend for the workspace store, behind the new `@melandlabs/workspace/postgres` entry point.

The SQLite store is a local/desktop backend: `better-sqlite3` is a native module and a synchronous driver, which a serverless sandbox cannot load and which blocks the event loop. A cloud deployment therefore had no way to keep its workspace index. This adds the Postgres backend the cloud path needs — same schema, same token scheme, same search semantics, a different wire protocol.

**What was added**

- `createPostgresWorkspaceStore({ connectionString })` — opens a store and creates the schema on the way in. The schema mirrors the SQLite one table for table (`workspace_resources`, `workspace_resource_versions`, `workspace_chunks`, `workspace_reference_edges`, `workspace_jobs`, `workspace_resource_facts`), with the differences Postgres forces: `INTEGER GENERATED BY DEFAULT AS IDENTITY` ids, `BIGINT` unix-second timestamps, and `JSONB` for `metadata` / `provenance`.
- The FTS5 mirror becomes a generated column — `search_vector tsvector GENERATED ALWAYS AS (to_tsvector('simple'::regconfig, index_text)) STORED` — over the *same* derived lexical text the SQLite backend feeds to FTS5, so both backends index the same tokens and a query that finds a document in one finds it in the other. A GIN index backs it.
- FTS5 query syntax is translated to `tsquery` by letting Postgres do the parsing: `phraseto_tsquery('simple'::regconfig, …)` turns a token string into exactly the phrase its own parser sees, the same way FTS5's tokenizer turns a quoted string into a phrase. `phraseto_tsquery` also never raises on odd input, so a token the parser cannot make sense of degrades to "no match" instead of an error.
- Semantic search uses `pgvector` when the extension is available (per-dimension child tables, mirroring the SQLite `vec0` tables), and degrades to lexical-only when it is not.
- The entry point deliberately does **not** pull in `better-sqlite3`: it is a separate export, so a serverless bundle never sees the native module. The build verifies this — `dist/postgres.js` contains no reference to it.

**What changed in the existing API**

The store contract is now asynchronous, because a Postgres round trip cannot be hidden behind a synchronous signature:

- `searchLexical(store, input)` and `searchSemantic(store, input)` return promises.
- `EmbeddingQueue.stats()` returns a promise.
- `distillResource` reads the source body through the store contract instead of the SQLite-only `__testDb` handle.

`SqliteWorkspaceStore` itself is untouched — its methods stay synchronous, because the desktop app depends on that. The bridge is `SqliteWorkspaceStoreAdapter`, which wraps the synchronous store into the async contract; `toWorkspaceStore(store)` normalises either backend. Every API function (`updateWorkspaceContext`, `searchWorkspaceContext`, `listWorkspaceResources`, `resolveWorkspaceCitation`, `distillResource`, `promoteFactsToPage`) now accepts either backend.

**Testing**

`test/postgres-store.test.ts` is gated on `WORKSPACE_POSTGRES_URL` and runs each test in its own Postgres schema, dropped afterwards. It needs a *direct* (unpooled) connection: a pooled gateway multiplexes client connections onto shared backend sessions, where a session-level `search_path` leaks between them. `test/postgres-tokens.test.ts` pins the FTS5 → tsquery mapping so a change to the tokenizer cannot silently desync the two backends.
